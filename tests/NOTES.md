# 仕様の曖昧さ、矛盾、テスト不能な点

推測では埋めていない。テストが決めた点は、`tests/CONTRACT.md` の［決定］を見る。

## 矛盾・曖昧（仕様の判断が必要）
1. **analysis_failed と定型の投稿**
   - R-16 と F-10 は、定型の投稿を `post_target` の実行だけに限る。
   - design 3 の表は、`analysis_failed` にも定型の「調査失敗」を投稿するとある。
   - スキーマは、`analysis_failed` と `route: out_of_scope` の組を禁じていない。
   - 対応：テストは `post_target` だけを見る。`analysis_failed` は、テストしない。
2. **対象外の state**
   - R-19 は「確定できなければ記録のみ」。design 3 は「PR特定不能は out_of_scope」。design 2.1 は「直接pushは、対象外（記録のみ）」。
   - 対応：gate のテストは、`out_of_scope` と `record_only` のどちらも許す。`route` は `out_of_scope` に固定した（決定）。
3. **mention の必須と「メンションなし」**
   - design 2.1 は「判定できないとき：メンションなし」。スキーマの `mention` は必須で、空文字を許さない。
   - botのログイン（`dependabot[bot]`）は、`mention` の正規表現に合わない。bot のPRやcronでは、context がスキーマに合わなくなる。
   - 対応：代替値を使う決定をした。値は、実装者が選ぶ。
4. **ワークフロー名**：テンプレートに `<workflow>` があるが、context.json に項目がない。環境変数 `TRIAGE_WORKFLOW_NAME` を決めた。
5. **行IDの形式**：`evidence/log.txt` の「行ID付き」の書式が未定。`L<n>: <原文>` と決めた。準備のスクリプトも、これに合わせる必要がある。
6. **network_error の確認**
   - 「evidence の行が典型的なメッセージを含む」は、いずれかか、すべてかが不明。「いずれか」と決めた（テストは、1行だけのevidenceで確認する）。
   - 典型的なメッセージの一覧は、例示だけ（3種）。大文字小文字、`connection refused`、`no such host` の扱いが未定。
7. **無害化の意味**
   - 未定の点：`@` を削除するかエスケープするか。リンクのテキストを残すか。`<script>` の中身を残すか。
   - S-04 は、`result.json` への適用だけを書く。ログから組み立てる引用への適用は、書かれていない。引用にも適用すると決めた。
   - 「文字数に上限」は、スキーマの `maxLength` で検証の失敗にするのか、切り詰めるのかが未定。後者は、スキーマ違反と二重になる。引用の長さの上限は、未定。
8. **Issueの探し方**：Issueの本文にフィンガープリントを埋める方法、追記先が複数ある場合、`fingerprint` が null の場合（準備が取れなかったとき）が未定。Issueの作成者の確認も、仕様にはない（R-21 はコメントの照合）。
9. **後続attemptの扱い**
   - 同じ run の、より後の attempt のコメントがある状態で、前の attempt を処理する場合が未定（再実行の遅延や順序の入れ替わり）。
   - 同じ run の前の attempt が複数ある場合は、最大の attempt を更新すると決めた。
10. **入口の判定の細部**
    - `pull_requests` が複数ある場合。
    - マージ済みPR経由のmainの失敗で、そのPRの作成者がbotの場合（R-02 の「botによる実行」の範囲）。
    - 紐づくマージ済みPRのベースブランチの確認。
    - `conclusion` が failure 以外の場合。
    - `actor` と `triggering_actor` の使い分けは、「初回は run_attempt が1」と解釈した。
11. **復旧の再確認（R-14）**：post.sh が再確認をするなら、`gh api` で実行履歴を読む必要がある。この契約の `gh api` に含めていない。後で足すときは、取れないときの挙動を決める必要がある（今は、読み取りの失敗は、書き込みなしで終了コード非0）。

## テストできない、または限界がある点
- **R-21 の照合その2（対象）**：実際のAPIは、そのIssueのコメントしか返さない。「別の対象のコメントが混ざる」は、スタブで作った状況。実装は `.issue_url` で確認するが、本物の環境では、パスの指定が実質の保証になる。
- **R-21 の限界**：`github-actions[bot]` は、同じリポジトリの、`GITHUB_TOKEN` を持つすべてのワークフローが共有する主体。AIのステップにもトークンがある（design 8）。作成者の確認では、偽のコメントを防げない。
- **F-13（同時実行）**：`concurrency` は、ワークフローの定義であり、スクリプトの単体テストでは見られない。コメントの一覧の反映遅れ（書いた直後の読み取りで見えない）も、テストできない。
- **スタブの忠実度**：応答の形は、公開APIの記憶による。ページ分割（100件超）は、再現していない。`--paginate` は無視する。
- **S-07（ハッシュ）、R-17 のメンション選択の実際、R-18 のサマリー**：範囲外。
- **スキーマ検証の二重管理**：`tests/lib/context_valid.jq` は、`context.schema.json` の手書きの写し。スキーマを変えたら、直す。ケース `t_G00` が、`schemas/examples/` との一致を見る。
- **未実行**：この納品で実施したのは、`bash -n` の構文確認と、固定JSONの `jq empty` だけ。テスト本体、スタブ、jq の検証器は、実行していない。初回の実行で、テスト側の誤りが見つかる可能性がある。
- **改行コード**：Windows で CRLF に変換されると、スクリプトが動かない。`tests/` に `.gitattributes`（`eol=lf`）を置く案がある。範囲外のため、作っていない。
